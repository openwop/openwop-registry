Catalog

Eight kinds of pack.

Each kind plugs into a different part of a host, and a host reads the kind before it loads anything. Choose a kind to see its packs.

Node packs ship reusable workflow building blocks — typed input/output handlers, control nodes (flow / branching / approval gates), and integrations (HTTP, storage, MCP). Authors drop them into the canvas at edit time; hosts load and verify them at runtime. See the packs spec spec for the manifest contract and the SRI + Ed25519 trust model. Mixed packs that also ship agents are flagged + agent.

How packs are checked

Change one byte, and it fails.

  1. 1 · SignedEvery version is signed.A detached Ed25519 signature (.sig) covers the canonical JSON of the pack.json inside the tarball, made with a key registered for that namespace.
  2. 2 · PinnedThe manifest pins its hash.The version manifest carries the tarball's SRI integrity hash, so a changed byte is caught.
  3. 3 · VerifiedThe host checks before it loads.A host in verified mode fetches the key its manifest names, checks that key may sign this namespace, and verifies the signature before unpacking (packs spec §Signing).

Verify a pack yourself

Each version manifest names its key in signing.keyId. Fetch that key from /keys/{keyId}.pub, confirm the pack's name falls in the key's namespaces, then verify the .sig against the canonical (JCS) bytes of the tarball's pack.json. The registry's own check does all of this:

git clone https://github.com/openwop/openwop-registry
cd openwop-registry
node registry/scripts/verify-signatures.mjs --tree v2

API

Read-only, and discoverable.

Clients resolve every path through the discovery document rather than hard-coding them.

  • /.well-known/openwop-registry discovery: every endpoint template
  • /v2/index.json the full pack catalog
  • /v2/packs/{name}/index.json one pack's metadata and versions
  • /v2/packs/{name}/-/{version}.json version manifest
  • /v2/packs/{name}/-/{version}.tgz tarball
  • /v2/packs/{name}/-/{version}.sig Ed25519 signature
  • /v2/packs/{name}/-/{version}.sbom.json software bill of materials
  • /keys/{keyId}.pub a signing public key

The /v1/ tree is still served, read-only, for clients that predate RFC 0177; new versions land only in /v2/. The discovery document lists both under endpoints.v1 and endpoints.v2.

A pack schema whose $id is https://packs.openwop.dev/{name}/{version}/<schema>.json resolves to the schema extracted from the signed tarball. The tarball is canonical and the mirrored URL is derived, so verify against the tarball when integrity matters (packs spec §The registry tree).

Publish a pack.

Build the pack, sign the version with a key registered for its namespace, and open a pull request. There is no write API on purpose. CI checks the manifest, the hash and the signature before merge, and a merge to main deploys it.
